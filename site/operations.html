Monitoring, backup and restore, security

Monitoring

Every container sends its logs straight to CloudWatch (one log group each: /kape/caddy, /kape/librechat, /kape/mongo, /kape/gateway, plus /kape/host for the server and the scheduled jobs), kept for 14 days. Metric filters turn the gateway's and Caddy's log lines into numbers, the CloudWatch agent adds memory and disk, and the scheduled jobs publish their own results.

The ten alarms, and why each threshold

All ten email me through the SNS topic kape-alerts, both when they go into alarm and when they recover.

AlarmFires whenWhy this threshold
kape-site-downThe minute-by-minute check of https://…/health fails 3 minutes in a row (no data also counts as down)Three misses rules out one slow request but still tells me within about 3 minutes; missing data counts because a dead server sends nothing.
kape-answers-failing3 or more questions fail in 5 minutesThe site can be "up" while every answer fails (expired key, quota); this catches the product being broken, not just the server.
kape-answers-slow90% of answers take longer than 10 s, in 2 of 3 five-minute periodsNormal answers take 1–3 s; 10 s is where a customer gives up. Using the 90th percentile ignores one odd slow answer.
kape-http-5xx5 or more server errors in 5 minutesA few errors happen during a deploy; five in five minutes means something is really wrong.
kape-cpu-highCPU above 80% for 15 minutesA t3.small earns CPU credits slowly; staying this high means a runaway process and would soon throttle the server.
kape-memory-highMemory above 85% for 10 minutesWith 2 GB and no room to spare, sustained 85% means a leak or a job that does not fit, before anything is killed.
kape-disk-highDisk more than 80% fullLeaves several GB and time to clean up before the database cannot write.
kape-backup-missingNo successful backup in 24 hours (no data also counts)Backups run nightly; one missed night is the earliest it can be noticed, and a silently broken backup is the worst kind.
kape-ec2-hardware-checkAWS's host check fails for 2 minutesAlso recovers the instance onto healthy hardware automatically.
kape-ec2-os-checkThe server's own status check fails for 3 minutesAlso reboots the instance automatically; a frozen server will not fix itself.

Proof that an alert reached a person

Every request is logged

brew-gateway writes one JSON line per question: the question, how long it took, whether it succeeded, the HTTP status, whether the answer was empty, and which gateway, content and model version answered. This line is from AWS, CloudWatch log group /kape/gateway, 2026-11-07 (E-09; the _aws block that follows it, used for metrics, is left out):

{"ts":"2026-11-07T05:45:06.400Z","service":"brew-gateway","event":"chat_request","level":"info",
 "requestId":"0631f894-54b1-4e0f-a1cc-645f9be4c7c2",
 "question":"What time does the Session Road branch open on Saturday?",
 "durationMs":1601,"httpStatus":200,"success":true,"emptyAnswer":false,"stream":false,"answerChars":55,

durationMs is how long it took, success and httpStatus whether it worked, and gatewayVersion, contentVersion (a fingerprint of the café documents) and model say exactly which version answered. Metric filters count these lines into the dashboard's request, error and latency graphs.

How the backup works

Every night at 02:00 Philippine time, infra/ops/backup.sh dumps the database (compressed), packs the uploads, writes a manifest with the number of documents in each collection and SHA-256 checksums of every file, and uploads all four files to s3://…/backups/<time>/. It checks that all four arrived, keeps three nights on the server, and publishes BackupSuccess; if anything fails it publishes 0 and emails me. An S3 lifecycle rule deletes backups after 14 days, and versioning is on for the whole bucket.

The restore test

infra/ops/restore.sh --test downloads a backup from S3, checks every file's checksum, restores the database into a separate copy (LibreChat_restoretest) so the live site is untouched, and compares the number of documents in every collection with the manifest. It runs by itself every Sunday at 03:30. The first run failed, which became the incident; after the fix it passes.

The live restore (restore.sh --live) follows the restore runbook: it stops LibreChat, replaces the database, puts the uploads back, and starts it again.

RPO and RTO

RPO (how much we could lose): up to 24 hours: anything written after the last 02:00 backup, which for a café FAQ assistant is a few chat histories. RTO (how long until it works again): about 5 minutes if the server is fine and only the data is lost (the restore itself took 13–14 s); about 30 minutes to rebuild a new server from the repository and Parameter Store and then restore.

Automations

All automation code is in the repository (infra/ops/, infra/cron/kape-lumen, .github/workflows/deploy.yml), and the README explains how to deploy them. The scheduled jobs are installed by the deploy script, so every deploy reinstalls the current version. Each job writes timestamped lines to /var/log/kape-automation.log, which is shipped to CloudWatch (/kape/host), publishes a metric, and emails me if it fails.

Incident: the restore test was killed (exit 137)

Summary. The first restore test on AWS died after 8 seconds. It looked like the server running out of memory; it was actually MongoDB hitting Docker's default limit of 1024 open files, crashing, and taking the restore down with it. Time to detect: under 1 minute. Time to fix: 3 minutes to a working restore, and the root cause found and fixed the same day.

Root cause

MongoDB ran out of file handles, not memory. Its storage engine keeps one file per collection and one per index. LibreChat's database has 60 collections, many with 5–12 indexes, and the restore test builds a second complete copy of them, several at a time. That went past Docker's default limit of 1024 open files per container. When the storage engine cannot open a file it stops the database on purpose, Docker restarted it, and the restore running inside the same container died with it. Exit 137 means "killed": the restore was a victim, not the cause.

The first guess (memory) was wrong, and the evidence says so: the kernel log shows no out-of-memory kill, and Docker reports oomkilled=false. Restoring one collection at a time made the test pass only because fewer files were open at once; with a bigger database the crash would return.

Customers were affected for about 3 seconds: the crashed MongoDB is also the live database. That was too short for the site check to fire, and no data was lost.

The fix, and evidence it worked

  1. Fix: the MongoDB container now gets an open-file limit of 64000, MongoDB's recommended minimum (ulimits: nofile in infra/docker-compose.yml, deployed automatically by GitHub Actions).
  2. Kept as a margin: the restore still runs one collection at a time.
  3. Prevention and detection: the restore test now runs every Sunday by itself, publishes RestoreTestSuccess and emails me if it fails, so a recurrence is caught within a week instead of on the day a real restore is needed. The runbook's Gotchas section says how to recognise it.

And unattended: the first scheduled restore test, on Sunday 2026-11-07 19:30 UTC (03:30 PHT), restored that night's backup with the new limit in place: OK in 14 s, counts match, with no crash and nobody watching (see Unattended runs).

What I learned

  • Read the failing service's own log before guessing. Exit 137 on a small server pointed at memory; MongoDB's log said "Too many open files" in plain words.
  • A workaround that turns the test green is not a root cause. I kept going after it passed.
  • Default limits are not production settings, and startup warnings are worth reading: MongoDB had been warning about the 1024 limit since it first started.
  • Editing a script directly on the server fixed the restore but blocked the next deploy. Fixes go through the repository; deploy.sh now says so when it happens.
